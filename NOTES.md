## 1. Native ETH: send / transfer / receive / fallback / failure modes

### There is only CALL

At the EVM level there is exactly one mechanism for moving ETH between accounts inside execution: the `CALL` opcode. Solidity's `transfer`, `send`, and `call{value:}` all compile to it — they differ only in compiler-inserted parameters and error handling:

| Solidity | Gas forwarded | On failure |
|---|---|---|
| `x.transfer(amt)` | 2300 (hardcoded) | reverts automatically |
| `x.send(amt)` | 2300 (hardcoded) | returns `false` — easy to ignore silently |
| `x.call{value: amt}("")` | all remaining gas (or specified) | returns `(bool, bytes)` — must check |

The 2300-gas stipend was a safety feature (enough to emit an event, not enough to reenter) that aged badly: opcode repricing (EIP-2929 etc.) means a recipient contract with a modest `receive()` can no longer run within 2300 gas, so `transfer` reverts and can permanently brick payments to that recipient. **Current best practice: `call{value:}("")` + explicit success check + checks-effects-interactions ordering + reentrancy lock where needed.** WETH9 still uses `transfer` in `withdraw()` (it predates the shift) — contracts with expensive `receive()` cannot withdraw from WETH directly.

The pattern audited protocols actually converge on goes one step further: **pull over push**. Instead of pushing ETH to the payee, credit a withdrawable balance and let the payee call `withdraw()`. This sidesteps every failure mode in the table simultaneously — no stipend issue, no sender-side reentrancy, no "recipient has expensive receive," no gas-repricing time bomb, and one stubborn recipient can't block a batch payout. Trade-off: two transactions and worse payee UX. (OpenZeppelin's `PullPayment`/`Escrow` were the v4 reference implementations; removed in v5 — the pattern is a mapping and a withdraw function, hand-rolled.) Scope the rule correctly, though: pull is *mandatory* only when a failed push would trap value (no alternate path) or block other payees (batch payouts). Push is fine when the recipient is singular and failure is recoverable — the workbook Escrow pushes in `release()`, safely, because a failed send reverts to Funded with `refund()` still open.

Note the payload distinction: `call{value: x}("")` — empty bytes — is what makes it a *plain transfer*, triggering the `receive`/`fallback` dispatch below. `call{value: x}(data)` with non-empty calldata is a *contract call with value attached*: dispatch goes to selector matching, not `receive()`. Beginners write `x.call{value: v}(abi.encodeWithSignature(...))` and wonder why the recipient's `receive()` never fired.

Related native things: `msg.value` = `CALLVALUE` opcode; balances are protocol state (`address.balance`), not a contract mapping; all amounts are integer **wei** (1 ETH = 10^18 wei; `1 ether` / `1 gwei` are just literal suffixes). Decimals exist only in UIs.

### Who can send/receive

Two account types, both hold wei balances:

- **EOAs**: send by signing a transaction with a `value` field (every ETH movement ultimately starts here); receive unconditionally — no code runs. *Caveat post-Pectra (EIP-7702):* an EOA that has signed a 7702 delegation has delegate code that runs on inbound calls — such an EOA **can** bounce a plain send if the delegate's `receive`/`fallback` reverts. "Unconditionally" now means "unless 7702-delegated, in which case the delegated contract's rules apply."
- **Contracts**: send only during execution via CALL; receive only through a payable path — a `payable` function, `receive()`, or payable `fallback()`. Otherwise incoming ETH reverts. (The "reject if not payable" check is Solidity-generated bytecode, not EVM-enforced.)

A plain EOA→EOA transfer involves no contract at all: `{to, value, data: 0x}`, flat 21,000 gas, pure protocol balance update.

**Forced ETH — the holes in a contract's right to refuse**: `selfdestruct(target)` pushes balance unconditionally; block fee recipient; pre-funding an address before deployment (predictable with CREATE2). Consequence: never key logic off `address(this).balance` matching internal accounting — track state explicitly. *Footnote (EIP-6780, Cancun):* the balance push remains unconditional — the forced-ETH surface is unchanged — but `SELFDESTRUCT` now clears code/nonce/storage **only if it runs in the same transaction as the contract's creation**. The old "selfdestruct to reset state / make room for a redeploy" trick is gone; readers who know the pre-Cancun rule will trip on this.

### receive() and fallback() dispatch

Solidity's dispatcher reads the first 4 bytes of calldata (function selector); `receive`/`fallback` catch what doesn't match:

```
msg.data empty (plain ETH send)
  → receive() if defined
  → else payable fallback()
  → else REVERT            ← why ETH "bounces" off standard ERC20s
msg.data non-empty
  → matching function selector
  → else fallback() if defined
  → else REVERT
```

- `receive() external payable` — fixed signature. By the time it runs the ETH is already credited; code can only revert to bounce it. An empty body (`receive() external payable {}`) is legitimate and load-bearing in wallet-style contracts (the workbook MultiSig needs it to be fundable at all). Production versions emit a Deposit event (cf. Gnosis Safe's `SafeReceived`) since plain transfers otherwise produce no logs.
- `fallback()` — "called a function I don't have." Its killer use: **proxies**, whose fallback `delegatecall`s everything to an implementation contract.
- Omitting both is a *feature* when unsolicited ETH is meaningless (workbook Escrow: `fund()` with exact price is the single audited entry point).
- Security: an attacker's `receive()` is reentrancy's front door — it executes mid-payment with full gas when you `call{value:}`. Defenses: state transition before external call, `nonReentrant` lock. A permissive payable `fallback` silently swallows typo'd calls that should have reverted.

### Native vs ERC20 — the distinction the shared name "transfer" blurs

- Native ETH: protocol-level state, no contract, built-in send, must opt in (payable) to receive.
- ERC20 `transfer`: an ordinary function on an ordinary contract updating a `mapping(address => uint256)`. Sending tokens is a transaction with `value: 0`. Recipients cannot opt out and get no notification (ERC721's `safeTransferFrom` + `onERC721Received` hook fixed that for NFTs). Failure modes are author-defined: returning `false` instead of reverting, USDT returning nothing, fee-on-transfer — hence SafeERC20.
- Typical ERC20s have **zero** payable functions and no receive/fallback — raw ETH sent to a token address bounces harmlessly.

| | Native ETH | ERC20 |
|---|---|---|
| EOA receives | always | always |
| Contract receives | only via payable path | always (no hook unless token adds one) |

## 2. WETH, and wrapping vs swapping

### WETH

Wrapped Ether: an ERC20 where 1 WETH is always redeemable for exactly 1 ETH. Exists because native ETH doesn't implement the ERC20 interface — protocols would need two code paths for everything. WETH9 (2017, unchanged, no admin/owner/upgrade, never hacked) is ~50 lines:

```solidity
receive() external payable { deposit(); }          // plain send auto-wraps
function deposit() public payable { balanceOf[msg.sender] += msg.value; }
function withdraw(uint wad) public {
    require(balanceOf[msg.sender] >= wad);
    balanceOf[msg.sender] -= wad;                  // effects before
    payable(msg.sender).transfer(wad);             // interaction (legacy transfer!)
}
```

- `deposit()` takes no parameter — the amount **is** `msg.value`, in wei. Credited unchanged to the mapping; works out 1:1 because WETH has 18 decimals, same scale as wei. (`decimals` is per-token cosmetics — USDC uses 6; mixing scales is a classic bug class.)
- `withdraw()` is not payable (nothing rides in); amount is an explicit wei-scale parameter. Safe against reentrancy purely by ordering — balance decremented before the send.
- Invariant: `address(this).balance >= totalSupply` — every WETH backed by actual ETH in the contract; redemption is code, no oracle or issuer.
- Also gives ETH an `approve`/`transferFrom` workflow, which native ETH lacks (you can't authorize a contract to pull ETH).
- Every EVM chain copies the pattern: WBNB, WPOL, WAVAX.

### Wrap ≠ swap

Wrapping is **mint/burn of the same asset in a different wrapper**: no counterparty, no price, no slippage, no fee, always exactly 1:1. A **swap** exchanges two *different* assets at a *market price* and requires someone on the other side — typically an AMM pool:

- Pool holds reserves of two ERC20s, supplied by LPs.
- Constant-product pricing: `x · y = k` — send Δx of one asset, receive whatever Δy keeps `(x+Δx)(y−Δy) ≥ k`, minus ~0.3% LP fee.
- Consequences wrapping doesn't have: price impact grows with trade size (slippage), rate changes constantly, LPs bear inventory risk for fees.

"Swap ETH for USDC" on Uniswap is both stitched together by the router in one transaction:

```
ETH ──(wrap 1:1, WETH9.deposit)──► WETH ──(swap, priced by x·y=k pool)──► USDC
```

Litmus test: **could the rate ever be anything but exactly 1:1?** Wrapper: no (redemption by construction). Swap: yes (the rate is the product). Third category: vault shares / stETH — issuance against backing, but rate drifts as yield accrues. Wrapper vs vault share vs traded pair sorts out most of DeFi at a glance.

## 3. The diamond: multiple inheritance and supportsInterface

When a contract inherits two bases that both implement the same function, Solidity refuses to guess — you must override explicitly and name both bases. Canonical occurrence: ERC165's `supportsInterface` when combining OpenZeppelin's `ERC721` (or extensions) with `AccessControl`:

```solidity
contract InterviewNFT is ERC721URIStorage, AccessControl {
    function supportsInterface(bytes4 interfaceId)
        public view override(ERC721URIStorage, AccessControl) returns (bool)
    {
        return super.supportsInterface(interfaceId);
    }
}
```

- ERC165 is the "what interfaces do you speak?" introspection standard — marketplaces call `supportsInterface(0x80ac58cd)` to ask "are you an ERC721?".
- `super` in Solidity follows **C3 linearization** of the inheritance graph (right-to-left of the `is` list), so a single `super.supportsInterface(id)` chains through *all* parents, each ORing in its own interface IDs. The boilerplate is compiler-mandated; the mechanism is why it works.

**Disambiguation**: this inheritance diamond is unrelated to the **Diamond Standard (EIP-2535)** — a proxy pattern where one contract routes function selectors to multiple implementation "facets," used to exceed the 24KB contract size limit and do granular upgrades. Same word, different concept; interviewers may probe for whether you know both.

## 4. EIP-712: typed structured-data signing

Standard for signing **structured data off-chain** such that (a) wallets can display what's being signed in human-readable form, and (b) contracts can verify the signature on-chain and act on it. Contrast with signing a raw hash — the wallet shows opaque hex, phishing-friendly.

Mechanics:

- **Domain separator**: hash of `(name, version, chainId, verifyingContract)` — binds a signature to one contract on one chain, preventing cross-contract and cross-chain replay.
- **Typed struct hash**: the data is hashed with its type definition, e.g. `keccak256("Permit(address owner,address spender,uint256 value,uint256 nonce,uint256 deadline)")` combined with encoded values.
- Final digest: `keccak256("\x19\x01" ‖ domainSeparator ‖ structHash)`; signed with the user's key; contract recovers the signer via `ecrecover` and checks it's the expected party. **Nonces** (tracked on-chain per signer) prevent replay of the same signature.

Where it appears:

- **Gnosis Safe**: owners sign an EIP-712 hash of the transaction off-chain; `execTransaction` verifies m-of-n signatures in a single on-chain transaction. Versus the workbook MultiSig's on-chain `approve(id)` per owner (n transactions), this is cheaper, faster, and only the executor pays gas. Standard answer to "how would you improve this multisig."
- **ERC-2612 `permit`**: gasless ERC20 approvals — sign a Permit off-chain, anyone submits it, contract sets allowance. Kills the separate approve transaction.
- Meta-transactions, order books (0x, Seaport), voting-by-signature.

Related smart-account facts (from the Safe discussion):

- Each CALL frame rewrites `msg.sender` to the immediate caller: EOA → Safe → target means the target sees **the Safe** as sender. That's what makes a multisig a first-class identity (can own tokens, hold roles, be an admin). `tx.origin` still points at the signing EOA — which is why `tx.origin` auth is an anti-pattern (breaks and endangers smart-account users).
- Safe's `operation` parameter: `Call` (target's own context) vs `DelegateCall` (target's *code* runs in the Safe's storage/balance/identity — can rewrite owners or drain it). MultiSend batching and modules use it legitimately; the Bybit hack (Feb 2025, ~$1.5B) was a malicious delegatecall signed via a compromised UI. Verify on the hardware wallet screen; treat `operation = 1` with extreme suspicion. Same primitive powers upgradeable proxies: *call = their context, delegatecall = my context*.

## call vs delegatecall

Both are EVM opcodes that execute another contract's code. The difference is **whose execution context** that code runs in:

| | `call` | `delegatecall` |
|---|---|---|
| Code executed | target's | target's |
| Storage read/written | **target's** | **caller's** |
| `address(this)` / balance | target | **caller** |
| `msg.sender` seen by code | the caller contract | **preserved** (original caller's caller) |
| `msg.value` | set per-call (`{value:}`) | preserved; cannot attach new value |
| ETH moved | yes, with `{value:}` | never |

Mnemonic: **call = run code in *their* house; delegatecall = borrow their code and run it in *my* house.** Delegatecall'd code can rewrite the caller's storage, spend its balance identity, `selfdestruct` it — total trust.

- Legit uses: proxies (below), libraries (`using ... for` external library calls are delegatecalls under the hood), Safe's `operation = DelegateCall` for MultiSend batching and modules.
- Attack surface: signing a Safe delegatecall to attacker code = handing over the Safe (Bybit, Feb 2025, ~$1.5B — malicious delegatecall behind a compromised signing UI). Any function that delegatecalls a user-supplied address is a rug by construction.
- Storage is addressed by **slot number, not name** — delegatecall'd code writes "slot 0", "slot 1"... whatever the caller keeps there. This is the root of every proxy storage rule below.

There's also `staticcall` (call with writes forbidden — what `view` calls compile to) and the near-obsolete `callcode` (delegatecall's broken predecessor).

## The proxy mechanism

An upgradeable proxy is a contract holding **state** whose `fallback()` delegatecalls every call to an **implementation** contract holding **logic**:

```
user ──call──► Proxy (storage, balance, address)
                 fallback() ──delegatecall──► Implementation (code only)
                 result/revert bubbled back
```

- Users only ever talk to the proxy address; state accumulates there. Upgrading = pointing the proxy at a new implementation. Address, balances, storage all persist.
- The implementation's own storage is never used (its code always runs against proxy storage). Its constructor ran only in its *own* context, so it's useless for initializing proxy state — hence the constructor/initializer split below.

### Storage rules (where upgrades go wrong)

1. **EIP-1967 slots.** The proxy's own bookkeeping (implementation address, admin) must not collide with implementation-declared variables at slot 0, 1, ... So it lives at pseudo-random fixed slots: `keccak256("eip1967.proxy.implementation") - 1` etc. Explorers use these slots to detect proxies.
2. **Append-only layout across versions.** V2 must keep every V1 variable at the same slot: never remove, reorder, or change the type of existing variables; only append new ones. Reordering silently reinterprets old data as the wrong variable — no error, just corruption. (This is the "preserve storage layout in V2" requirement in exercise 08's TODO.)
3. **Storage gaps.** Upgradeable *base* contracts reserve `uint256[50] private __gap;` so the base can add variables later without shifting every child's slots.
4. **No initialized state outside initializers.** Field initializers (`uint x = 5;`) and constructors set *implementation* storage, which the proxy never sees. `constant`/`immutable` are fine — they live in code, not storage.
5. Tooling (`@openzeppelin/hardhat-upgrades`, foundry's `openzeppelin-foundry-upgrades`) diffs layouts between versions and blocks unsafe upgrades — use it; humans miss slot shifts.

### Constructor → initializer

Since constructors can't touch proxy storage, upgradeable contracts use an `initialize()` function guarded by OZ's `Initializable` (`initializer` modifier = run-once latch stored in proxy storage). Two footguns:

- **Uninitialized proxy**: anyone can front-run and call `initialize()` first, becoming owner. Initialize atomically at deployment (proxy constructor calls it).
- **Uninitialized implementation**: the bare implementation contract is also live on-chain; someone can initialize *it* directly and, in older UUPS versions, upgrade-then-selfdestruct it, bricking every proxy pointing at it. Fix is exercise 08's odd-looking constructor:

```solidity
constructor() { _disableInitializers(); }   // locks the implementation itself
function initialize(address owner_) external initializer {
    __Ownable_init(owner_); __UUPSUpgradeable_init();
}
```

## The upgrade patterns

### Transparent proxy (TransparentUpgradeableProxy)

Upgrade logic lives **in the proxy**. Problem it solves: function selector clashes — if the proxy had a plain `upgradeTo()`, an implementation function with the same selector would be unreachable. Solution: the proxy routes by caller — **admin calls hit proxy admin functions, everyone else falls through to the implementation** (admin can't use the app; users can't upgrade). Modern OZ deploys a dedicated `ProxyAdmin` contract as the admin. Costs: extra deployment, plus an admin-check SLOAD on every call. The battle-tested default for years; still common.

### UUPS (EIP-1822 / ERC-1967, what exercise 08 uses)

Upgrade logic lives **in the implementation**: `upgradeToAndCall()` is inherited from `UUPSUpgradeable` and executes via delegatecall like any other function, writing the EIP-1967 slot in proxy storage. The proxy itself is minimal (ERC1967Proxy: just fallback + slot). Authorization is a hook you must override:

```solidity
function _authorizeUpgrade(address) internal override onlyOwner {}
```

- Cheaper calls (no admin check), cheaper proxy deployment; upgrade authorization is expressive (roles, timelocks, votes).
- Risk: ship a V2 that *forgets* `UUPSUpgradeable`/`_authorizeUpgrade` and the chain of upgrades ends — permanently frozen on V2. (OZ's `upgradeToAndCall` does a rollback-style check to catch this.) An overly-permissive `_authorizeUpgrade` is instant total compromise.
- Current OZ recommendation for new projects.

### Beacon proxy

Many proxies read their implementation address from one shared **beacon** contract instead of their own slot. Upgrade the beacon once → every proxy upgrades simultaneously. For fleets of identical contracts (one-vault-per-user, one-escrow-per-deal). Trade-off: beacon owner is a single point controlling all instances; each call pays an extra external `staticcall` to the beacon.

### Minimal proxy / clones (EIP-1167) — *not* upgradeable

45-byte bytecode that delegatecalls a fixed, hardwired implementation. No slot, no upgrade — it's a **cheap deployment** pattern (~45k gas vs 100k+ per full deployment), the "factory of escrows" middle ground from the escrow singleton-vs-instances discussion. Pair with initializer since constructors don't run for clones.

### Diamond (EIP-2535)

One proxy, **many** implementations ("facets"): a selector→facet mapping routes each function independently; upgrades add/replace/remove selectors piecemeal. Solves the 24KB code-size limit and enables granular upgrades; costs significant complexity (shared storage via storage-struct-at-fixed-slot patterns, harder audits, weaker tooling). Distinct from the *inheritance* diamond (the diamond section above).

## Choosing (interview framing)

- Don't need upgrades? **Don't use a proxy** — immutability is a feature; every proxy adds an admin-key risk users must trust.
- Single app contract → **UUPS** (OZ default recommendation), `_authorizeUpgrade` behind a multisig + timelock.
- Fleet of identical instances → **clones** if never upgrading, **beacon** if upgrading together.
- Legacy/maximum-tooling-compatibility → **transparent**.
- Genuinely too big / modular upgrade surface → **diamond**, reluctantly.

Governance hygiene regardless of pattern: upgrade admin = multisig (see Safe notes) + timelock, so users can observe a pending upgrade and exit; emit `Upgraded` events (ERC-1967 standard); verify new implementations on-chain before pointing at them.

## EVM vs Solidity: what's protocol and what's compiler fiction

The EVM's contract-facing surface is tiny; nearly everything "Solidity" is convention the compiler lowers onto it. The layering — protocol / compiler convention / application convention (ERCs) — is the organizing map.

**What the EVM actually provides:**
- Accounts with balance, nonce, code, and flat 256-bit → 256-bit storage
- The CALL family (call / delegatecall / staticcall / create) moving value + opaque bytes between contexts
- A stack machine over 256-bit words, `LOG0–4`, `REVERT` with return data, gas metering, journaled state with rollback

**What is pure solc fabrication, compiled down to the above:**

| Solidity concept | What it really is |
|---|---|
| Functions & selectors | a dispatcher jump table over the first 4 calldata bytes — convention, not mechanism |
| Types (`uint8`, `address`, `bool`) | masking/cleanup conventions over 256-bit words |
| Checked arithmetic (0.8+) | emitted overflow-test-and-revert sequences around plain `ADD`/`MUL` |
| `mapping`, dynamic arrays, structs | storage-slot addressing schemes (`keccak(key ‖ slot)` etc.) — the EVM only sees `SLOAD`/`SSTORE` of computed slots |
| `payable` / non-payable | an inserted `CALLVALUE`-must-be-zero check, or its absence |
| `receive` / `fallback` | branches of the same generated dispatcher |
| Modifiers, inheritance, `super`, C3 | source-level macros — flattened into one bytecode; no runtime trace |
| Events | `LOG` opcodes plus an ABI convention for topic hashing |
| `require` / custom errors | `REVERT` carrying ABI-encoded return data (errors reuse the 4-byte-selector trick) |
| Interfaces / ABI | entirely off-chain agreement; the chain never checks them |
| `immutable` | deploy-time byte-patching of the runtime code |

Thin wrappers where the layers touch directly: `msg.sender` → `CALLER`, `msg.value` → `CALLVALUE`, `block.timestamp` → `TIMESTAMP`.

**Consequences:**
1. **The EVM enforces none of the conventions.** Nothing stops a contract interpreting calldata differently, lying about its ABI, or reverting where it advertised `view`. Cross-contract trust is trust in bytecode behavior — hence source verification, ERC-165, and `code.length` checks (calling an address with no code trivially "succeeds" with empty returndata).
2. **Interop is a social contract between compilers.** Solidity, Vyper, Huff, and hand-written bytecode compose on-chain solely because they chose the same ABI. Languages are replaceable precisely because none of the language reaches the protocol.
3. **Implement the primitives, get the language for free.** An EVM implementation needs CALL semantics, storage journaling, gas, and the fee schedule — every Solidity feature then works automatically, because solc leaves nothing else behind. You never implement `payable`; you implement `CALLVALUE`, and `payable` emerges.
